# 결제 데이터·API 인수인계

① 결제 데이터·API가 ② 증빙 분석, ③ 상태·문의자료, ④ 화면으로 이어지는 흐름을 확인하기 위한 문서입니다. 기존 합성 결제 `PAY-001`~`PAY-003`과 전액 취소 계약을 사용합니다. 새로운 합성 데이터 설계, 실제 AI 호출, AWS 배포는 이번 검증 범위에 포함하지 않습니다.

## 조회와 타임라인 계약

`GET /api/payments`는 `PaymentView[]`, `GET /api/payments/:id`는 해당 거래의 `PaymentView`를 반환합니다. 같은 시점의 목록 항목과 상세 응답은 같은 거래 정보·`events`·계산 상태를 제공합니다. 없는 거래는 `404 NOT_FOUND`입니다.

각 이벤트는 `id`, `kind`, `date`, `source`, `label`을 가집니다. 날짜는 해당 출처의 사건 날짜이며 `YYYY-MM-DD` 형식입니다. UI에서 시간순으로 표시하되 날짜만 보고 다른 종류의 사건을 만들어서는 안 됩니다.

| `kind` | 의미 | 상태 판단과의 관계 |
| --- | --- | --- |
| `payment` | 결제일 | 취소·카드 반영의 근거가 아님 |
| `cancel_requested` | 쇼핑몰의 취소 요청 접수일 | 가맹점·카드 확인의 근거가 아님 |
| `merchant_cancel` | 고객이 확인한 증빙의 가맹점 취소일 | 이벤트만으로 판단하지 않고 유효한 고객 확인 증빙을 확인 |
| `card_cancel` | 합성 카드 기록의 전액 취소 반영일 | 유효한 카드 기록으로 카드 상태를 독립 판단 |

기존 3건의 초기 상태는 다음과 같습니다.

| 거래 | 주문번호·금액 | 사건 날짜 | 초기 가맹점 / 카드 |
| --- | --- | --- | --- |
| `PAY-001` | `ORDER-001` / 50,000 KRW | 결제 11/15 | 미확인 / 미확인 |
| `PAY-002` | `ORDER-002` / 32,000 KRW | 결제 11/14 → 요청 11/15 → 가맹점 11/16 → 카드 11/18 | 확인 / 확인 |
| `PAY-003` | `ORDER-003` / 18,000 KRW | 결제 11/17 → 요청 11/18 | 미확인 / 미확인 |

위 날짜의 연도는 2026년입니다. `PAY-001`에는 요청 접수 자료가 없으므로 요청일을 채우지 않습니다. 증빙 연결은 기존 요청 기록을 보존하고 증빙의 취소일로 가맹점 이벤트를 추가합니다. 요청일을 취소일이나 카드 반영일로 대체하지 않습니다.

## 분석에서 고객 확인·연결까지

1. ④가 `POST /api/evidence/analyze`에 텍스트 또는 캡처를 보냅니다. JSON 텍스트와 FormData 입력 형식은 [API 문서](API.md)를 따릅니다.
2. ②가 `fields`와 `candidatePaymentIds`를 반환합니다. 확인되지 않은 필드는 생략하며, 모의 분석 결과는 테스트에서 `createApp({ evidenceAnalyzer })`로 주입합니다. 모의 성공은 실제 AI 호출 성공을 뜻하지 않습니다.
3. 분석 성공·실패·재시도는 모두 결제 저장소를 읽기 전용으로 다룹니다. 분석 응답만으로 `evidence`나 취소 이벤트를 추가하지 않습니다.
4. ④가 추출값을 보여주고 고객이 값을 수정하고 결제 후보를 선택하게 합니다. 재분석·값 수정·후보 변경 후에는 확인 체크를 해제하고 다시 확인받습니다.
5. 고객 확인 후 `POST /api/payments/:id/evidence`를 별도로 호출합니다. `candidatePaymentIds`는 선택을 돕는 정보이며, 서버는 실제 연결 대상 `:id`의 주문번호·금액·통화·결제일을 다시 검사합니다.

`PAY-001` 연결 요청 예시는 다음과 같습니다.

```json
{
  "orderNumber": "ORDER-001",
  "amount": 50000,
  "currency": "KRW",
  "cancelledOn": "2026-11-19",
  "confirmed": true
}
```

| 응답 | 조건 | 저장 결과 |
| --- | --- | --- |
| `400 INVALID_INPUT` | `confirmed`가 `true`가 아님, 필수값·금액·통화·날짜 형식이 유효하지 않음 | 전체 결제 기록 유지 |
| `409 PAYMENT_MISMATCH` | 선택한 결제와 주문번호·전액 금액·통화가 다르거나 취소일이 결제일보다 이른 경우 | 전체 결제 기록 유지 |
| `409 DUPLICATE_EVIDENCE` | 같은 결제에 같은 취소일 증빙이 이미 연결됨 | 기존 증빙·이벤트 유지 |
| `201 PaymentView` | 고객 확인과 연결 검증 통과 | 대상 거래에 고객 확인 증빙·가맹점 이벤트 추가, 다른 거래 유지 |

현재 통화는 KRW만 지원하므로 다른 통화 입력은 형식 검증에서 `400`으로 거절합니다. 취소일은 결제 당일도 허용합니다. 성공 시 서버가 증빙 ID·`source: "customer_confirmed"`·`confirmedAt`을 부여하고, 추가한 가맹점 이벤트는 같은 증빙 ID를 사용합니다.

③은 고객 확인 증빙으로 가맹점 상태를, 카드 기록으로 카드 상태를 각각 계산합니다. `PAY-001`이나 `PAY-003`에 증빙만 연결하면 가맹점은 확인, 카드는 미확인입니다. 요청 접수 또는 가맹점 증빙만으로 환불 완료를 표시하지 않습니다. ④는 성공 응답의 `status`, `nextAction`, `inquirySummary`를 반영합니다.

## API 회귀 검증

[PR #22의 테스트 파일](https://github.com/chohaeminn/aws-team3/pull/22/files)은 기존 결제 3건과 모의 분석기를 사용합니다. 아래 네 검사는 #22 브랜치에서 실행했습니다.

| 검증 흐름 | 확인할 계약 |
| --- | --- |
| 모의 분석 → 미확인 연결 거절 → 다른 거래 연결 거절 → 올바른 확인 연결 | 분석·거절 시 전체 저장소 불변, `400`·`409`·`201`, 대상 거래만 갱신, 목록·상세 일치, 요청일 미생성 |
| `PAY-003` 증빙 연결 | 11/18 요청의 ID·날짜·출처·문구 보존, 11/19 가맹점 이벤트만 추가, 카드 미확인 유지 |
| `PAY-002` 증빙 추가 | 기존 증빙·요청·카드 기록 보존, 가맹점·카드 확인 상태 유지, 다른 거래 불변 |
| 모의 분석 실패 후 동일 FormData 재시도 | 텍스트·이미지 바이트가 두 번 모두 동일하게 분석기에 전달, 실패·성공 후에도 전체 결제 기록 불변 |

기존 `tests/refund.test.ts`의 초기화 검증과 `tests/paymentStatus.test.ts`의 출처별 상태 검증도 함께 실행합니다. `POST /api/demo/reset`은 기존 3건의 증빙·이벤트·계산 상태를 초기 데이터로 복구합니다. 서버 재시작도 메모리 데이터를 초기화합니다.

```sh

npx tsx --test tests/paymentHandoff.test.ts
npm run typecheck
npm test
npm run build
```

PR #22의 커밋 `ec78ec7`에서 Windows와 Node.js 22.17.1로 회귀 테스트 4개를 포함한 전체 37개가 통과했고, 타입 검사와 빌드도 성공했습니다.

## 브라우저 검증 결과

2026-11-23, Windows에서 `main`의 `f180a65`를 빌드한 뒤 독립된 로컬 서버와 새 Chrome 158.0.8127.36 세션을 사용했습니다. Playwright가 화면의 버튼·입력란을 조작했습니다. 문의자료는 앱의 복사 버튼을 누른 뒤 별도 탭의 빈 텍스트 입력란에 `Ctrl+V`로 붙여넣어 비교했습니다.

같은 절차를 직접 확인하려면 `npm ci`와 `npm start`를 실행하고 `http://localhost:3000`을 엽니다. 기존 시연을 진행한 서버라면 자신의 로컬 시연 서버에서 먼저 초기화합니다.

| 순서 | 화면에서 할 일 | 확인한 결과 |
| --- | --- | --- |
| 1 | 초기 상태에서 세 거래를 차례로 선택하고 진행 상태와 타임라인을 기록합니다. | 위 초기 상태 표와 일치했습니다. PAY-002에는 11/14 결제, 11/15 요청 접수, 11/16 가맹점 취소, 11/18 카드 반영이 각 출처와 함께 표시됐습니다. PAY-003에는 11/17 결제와 11/18 요청만 있었습니다. |
| 2 | PAY-001의 증빙 등록 탭에서 합성 예시를 불러옵니다. 확인 체크 후 금액을 49999로 수정하고 50000으로 되돌립니다. 다시 체크해 연결합니다. | 최초 체크 전에는 연결 버튼이 비활성이었고 수정하자 체크가 풀렸습니다. 금액을 되돌린 뒤에도 다시 체크해야 연결됐습니다. 연결 후 11/19 가맹점 기록만 추가됐고 카드는 미확인으로 남았습니다. |
| 3 | PAY-001의 문의자료를 복사해 빈 텍스트 입력란에 붙여넣습니다. | 화면과 붙여넣은 내용 17줄 전체가 일치했습니다. ORDER-001, 50,000 KRW, 11/19 취소일, 고객 확인 증빙 출처, 카드 반영 미확인 문구를 확인했습니다. |
| 4 | PAY-002를 선택하고 같은 방식으로 복사합니다. | 화면과 붙여넣은 내용 17줄 전체가 일치했습니다. ORDER-002, 32,000 KRW, 11/16 취소일, 카드 반영일 11/18과 출처 ‘합성 카드 취소 기록’을 확인했습니다. |

## 후속 담당자가 확인할 부분

- **상태·문의자료 담당**은 3·4단계의 복사 결과를 비교하면 됩니다. PAY-001은 가맹점 증빙만 있고, PAY-002에는 별도로 카드 반영일과 그 출처가 있습니다.
- **UI 담당**은 2단계의 수정 후 재확인과 6단계의 시연 복원을 같은 순서로 재현할 수 있습니다.
- **AI 담당**은 PR #22에서 분석 입력·응답과 저장 시점을 확인할 수 있습니다. 이번 브라우저 실행은 합성 예시와 고객 확인 흐름을 검증했습니다. 실제 Gemini 이미지 분석·호출 한도 오류, 브라우저에서의 분석 실패 후 재시도, AWS 배포 환경은 미검증입니다. 통합 검증은 [팀 이슈 #18](https://github.com/chohaeminn/aws-team3/issues/18)에서 추적합니다.
